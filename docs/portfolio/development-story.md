# 개발 과정과 문제 해결

2026년 1월~10월의 개발 과정을 작성자의 회고와 현재 소스를 바탕으로 정리했습니다. 단계별 정확한 날짜는 기록하지 않았으며, 아래 순서는 개발 순서입니다. 실험 결과 중 사진·영상·파형과 연결되지 않은 내용은 작성자 관찰로 구분합니다.

## 프로젝트의 출발점

임베디드 취업을 준비하면서 하드웨어와 소프트웨어를 함께 이해하는 경험을 쌓고자 했습니다. STM32F103RB 개발보드 제작을 다룬 책·블로그를 통해 클럭, 전원, USB, 리셋 회로를 학습했지만 당시에는 PCB 배치 단계에서 중단했습니다.

이후 해외 전자공학·BLDC 제작 영상을 보며, 범용 개발보드보다 특정 기능이 있는 보드를 완성해 보고자 ESC 제작을 시작했습니다. 처음에는 자체 FCU와 연결한 소형 드론을 목표로 했고, 진행하면서 이번 결과물의 범위를 ESC와 센서리스 구동으로 좁혔습니다.

초기 개발보드는 STM32F103RB였고 현재 자체 PCB는 STM32F103C8 계열입니다. 이는 작성자가 확인한 단계 구분이며, 현재 `.ioc`와 회로도의 C8 표기와 일치합니다.

초기의 게이트 파형 전압은 기억에 남아 있지만 측정 기준점과 파형 자료가 정리되지 않았습니다. 따라서 특정 전압을 근거로 VGS나 드라이버 성능을 검증했다고 기록하지 않습니다. 초기 Vcom 회로의 구체적인 연결 방식도 당시 회로도 확인 전에는 재구성하지 않습니다.

## 사례 1. USB 풀업 경로의 실물 오류 수정

**증상:** USB 인식에 문제가 있었고, 풀업 연결을 제어하는 MOSFET의 풋프린트 적용 오류를 확인했다고 회고했습니다.

**조치:** 해당 MOSFET을 제거하고 배선으로 풀업 경로를 연결했습니다. 추가로 AI가 제안한 USB 재인식용 초기화 코드를 적용했습니다.

**관찰 결과:** 패치와 코드 적용 후 인식 문제가 해소되었다고 관찰했습니다. 현재 `main.c`에는 PA12를 GPIO 출력으로 설정하여 약 100ms LOW로 유지한 뒤 USB를 초기화하는 처리가 있습니다.

**남은 기록:** MOSFET 부품 번호, 잘못 대응된 핀·패드, 패치 전후 사진, 실제 변경 후 회로도. 하드웨어 수정과 초기화 변경 각각의 효과는 분리 검증하지 않았습니다. 모든 호스트·리셋 조건에서 USB 인식을 보장하는 결과로 해석하지 않습니다.

## 사례 2. 고듀티 ZC 관측과 비교기 경로 활용

**증상:** ADC 기반 구동에서 고듀티 영역의 ZC 관측이 어려웠습니다. 비교기에서도 PWM에 따른 다중 에지가 발생해 타이밍 정보로 사용하기 어려웠습니다.

**당시 가설:** Vcom과 상전압 입력의 충·방전 응답 차이, ADC 샘플링 간격과 취득 위치가 영향을 준다고 생각했습니다. 고듀티는 듀티·속도·샘플링 위치가 함께 변하는 조건이므로, 원인을 단순히 20kHz 샘플링만으로 확정하지 않습니다.

**조치:** Vcom 측 커패시터를 실물에서 제거했습니다. 고듀티 영역에서 비교기 에지가 비교적 단일하게 관찰되어 타이머 입력 캡처 기반 처리를 활용했습니다. 커패시터 제거는 당시 파형을 바꾸어 보기 위한 탐색적 변경이었고, 사전에 모델과 계산으로 도출한 최적화는 아니었습니다.

**관찰 결과:** 기존에 어려웠던 CCR 1300 부근을 넘어 CCR 1750까지 모터 구동을 관찰했습니다. 현재 코드는 CCR 1300을 기준으로 ADC와 비교기 ZC 처리 경로를 선택합니다. 단, 최초 성공 당시 소스와 현재 작업본의 동일성은 확인하지 않았습니다.

**남은 기록:** 제거한 커패시터 번호·용량, 수정 전후 Vcom/상전압/비교기 출력 파형, 실제 정류 시점. 단일 에지처럼 보이는 것이 정확한 ZC 검출을 뜻하는지는 별도 검증이 필요합니다.

## 구현 기여와 참고 범위

- 회로 작성, BOM 작성, PCB 배치·배선은 직접 수행했습니다.
- Buck·LDO는 데이터시트 예제 회로를, MCU 주변회로·BEMF 회로는 책·블로그·영상을 참고했습니다.
- PCB는 부품별 데이터시트 배치 지침과 TI 평가보드 Gerber 등을 참고했습니다. 설계 지침을 모두 만족했다는 검사 결과는 아닙니다.
- MOSFET·게이트 드라이버는 기존 영상·프로젝트의 사용 사례에서 선정하고, 이후 AI를 통해 선정 이유를 학습했습니다. 독립적인 후보 비교·최적 선정 결과로 설명하지 않습니다.
- SMT는 외주 의뢰했고 커넥터 납땜과 실물 수정은 직접 수행했습니다.
- 펌웨어는 브레드보드 단계의 코드에서 확장하며 AI의 도움을 받았습니다. AM32를 참고하려 했으나 코드 규모와 하드웨어 차이 때문에 체계적인 분석·이식까지 진행하지 못했습니다.

## 배운 점

초기에는 문제를 만날 때 AI의 제안을 바로 적용하며 시행착오를 반복했습니다. 동작시키는 데 집중하면서 근거와 상태를 충분히 기록하지 못한 점이 아쉬움으로 남았습니다.

이후 데이터시트와 기존 설계, 실제 제품을 기준으로 삼는 것이 중요하다고 느꼈습니다. 앞으로는 다음 순서로 개발하려 합니다.

1. 관련 오픈소스·평가보드·데이터시트를 찾아 먼저 읽습니다.
2. 현재 하드웨어와 참고 설계의 차이를 정리합니다.
3. 적용할 변경의 이유와 예상 관측 결과를 적습니다.
4. 파형·로그로 결과를 확인하고 변경 전후를 보존합니다.

AI는 자료 탐색과 설명·코드 작성을 보조하는 데 활용하되, 제안을 채택하는 근거는 원자료와 측정으로 확인하려 합니다. 기존 구현을 이해하고 자신의 하드웨어에서 재현하는 것 역시 중요한 개발 경험으로 받아들이게 되었습니다.
